# EH_Archive_tool 批量请求对照

## 实际调用流程

先筛选候选并读取按项缓存 → 把未命中项切成批次 → 用线程池同时执行若干批次 → 每批发一次普通 `/chat/completions` 请求 → 按返回项匹配输入、保存成功结果 → 保留失败项以便后续处理。

它使用应用内分批调用，没有在这条链路使用服务商异步 Batch API。流式开关只改变每批响应的接收方式。

| 环节 | EH_Archive_tool 当前实现 | 本项目当前实现 |
| --- | --- | --- |
| 批大小 | 按任务分别配置，如作者解析、作者归并、关系维护；作者解析通常以 25 项为默认值，其他任务各自有默认值，性能配置也可覆盖 | 单本语义整理使用「每次请求解析本数」，默认 8；配对判断每请求一对 |
| 并发 | 独立的 `ai_max_concurrency`，CLI 默认 3；同时处理的是批次数 | 独立的「同时请求数」，用于语义整理和配对两个阶段 |
| 调度 | `iter_limited_parallel` 每次提交一个大小不超过并发数的窗口；窗口内按完成先后收集，整个窗口结束后再提交下一窗口 | 固定数量的异步处理循环；某个循环完成一个批次后立即取下一个，无需等待同窗口其他请求 |
| 输入 | 各阶段只发送需要的字段；作者解析用短 `slot_id` 对应本批成员，再发送原名、标题、类型和作者解析提示 | 每本发送标题、作者、语言、卷话、刊载、版本等语义字段；当前返回格式还要求原文引用 |
| 单批输出处理 | 作者解析逐项按 `slot_id` 匹配，特定情况下以唯一原名匹配；各项写入审核记录，其中 `correct` 项写入解析缓存，遗漏项或失败项保留 | 整批通过语义校验后才保存其中每本的缓存；一条不匹配的引用会使整批结果被拒绝 |
| 请求失败重试 | 各阶段的 `ai_retries` 控制重试次数，CLI 默认 2；`ai_retry_sleep` 默认 2 秒，等待按 `基础等待 × 2^(尝试序号−1)` 增加 | 兼容 API 的 429/502/503/504 最多重试 1 次；其他网络或结果校验失败不会本轮自动重试 |
| JSON 修复 | `ai_chat_number` 控制额外对话修复轮次；JSON 提取失败时追加原回复和简短修复要求 | 当前严格校验，失败记录错误，不追加对话修复 |
| 流式 | `ai_stream` 可配置；客户端拼接 SSE，检测到明确不支持流式或返回格式时可能回退 | 本次新增兼容 API 的流式开关；保留所选模式，拒绝流式时由用户关闭后测试，不增加隐式回退请求 |

## 两个容易误读的细节

1. 作者解析有处理失败项的轮次结构，但当前 `_retry_batch_sizes()` 只返回原始批大小，不会自动从 25 缩到 10、5、1。重试目标路径会依据批大小限制并发为至多 3、2 或 1；这不等于自动按 token 或 429 调整所有请求。
2. 批次全部发完不等于每项都成功。该项目分别维护已解决成员、缺失成员、失败成员及按项缓存，后续可以只处理未解决项。它的结果类型和本项目不同，不能直接照搬其宽松匹配来替代本项目的证据校验。

## 值得借鉴的部分

- 精简每阶段输入和输出，尤其减少模型重复抄写标题、刊载结构和引用原文，降低每本输出开销。
- 让一批中合法的书籍结果独立保存，错误引用只影响对应书籍；继续校验每本事实及其证据。
- 为失败项提供单独重试入口；对可恢复请求错误使用可配置的等待，而不是立即重复发送。
- 日志显示批次编号、成员数量、批次完成数、成功/失败成员数和缓存命中数，便于区分批处理进度与单本进度。

以上批处理优化是本次阅读所得，尚未移植。本次实际修改为兼容 API 的流式开关与接收、用量统计、取消及缓存兼容。
